PV data pipeline

How the synthetic PV time series of the 90 parks are built: where every input comes from, where it is stored, and how the pipeline checks whether it is already there. Every step follows the same pattern. It looks first, fetches only what is missing, and never rewrites what exists.

Generator ~/Work/synthetic_re_data_generation · as of 3 November 2026 · release parks_pv_v3 (selection v3)

external source pipeline step present: skip missing: fetch and store

The basic pattern

Every step runs this loop for every park of the selection. Finished files are renamed only at the very end, so an interrupted run never leaves a half-written file that the next run would count as present. Any run can therefore simply be restarted.

The flow in four phases

The phases build on each other. Phase 1 is done by hand. Phases 2 to 4 are scripts that can be restarted at any time. Paths starting with $DATA_ROOT live on the NVMe of l1, see Directories.

Database

PostgreSQL database WeatherDB. The connection comes from the environment variable WEATHER_DB_URL. It is never in the code because it holds the password. A systemd service does not inherit it and needs it in an override file.

Commands

Check and fetch inputs

# WeatherDB connection from the shell environment
eval "$(grep '^export WEATHER_DB_URL' ~/.bashrc)"
export PV_RELEASE_NAME=parks_pv_v3

# inventory only: what is missing per park?
synthre/bin/python scripts/pv/run_parks_pv_v2.py prepare --dry-run

# fetch everything missing (long runs with nohup)
nohup synthre/bin/python scripts/pv/run_parks_pv_v2.py \
  prepare --steps site,cams,correct > prepare_cams.log 2>&1 &
nohup synthre/bin/python scripts/pv/run_parks_pv_v2.py \
  prepare --steps icon > prepare_icon.log 2>&1 &

# ICON runs for the forecasts later
... prepare --steps icon --icon-hours "06 12 15"

Not automated yet

  • Geometry is not part of prepare yet. geometry_release_states.py fetches its tiles itself, with the same cache check. Measuring is a run of its own per version.
  • Thuringia: the portal sits behind a CAPTCHA. Tiles are placed by hand in inputs/geodata/th/{laser,dgm1,dop20}/; the fetcher only reads the cache.
  • Release runner and geometry script still read parks_pv_v2 as a fixed name. This is being switched to parks_pv_v3.
  • Waiting times: CAMS depends on the ADS daily quota, ICON on NAS throughput. That is why both live in prepare and not in generate. The synthesis should stay fast and reproducible and never wait for an external service.
  • Without corrected CAMS, generate falls back to the raw CAMS values hour by hour and flags those hours. For a new park, prepare should therefore be complete first.

Confidential and never in a repository: site lists with coordinates and the value of WEATHER_DB_URL.
